# orchestraty

The main package: the `orch` command, the hook shims, the coordinator, the live map, the overlap rules and the notes that keep parallel coding-agent sessions aware of each other.

**Status: Phase 1, early access.** The coordination core works end to end: `orch init` installs the hooks and watches the repository it runs in; the coordinator, which the hooks start when needed, keeps a live map of what each session has changed, runs the overlap rules, and writes each note in advance for the session that must hear it; the hooks hand the notes to the agents. With two real Claude Code sessions, every note reaches its agent, ready within a second of the change. Codex and Antigravity are built; not yet tested with the real agents (see [Agents](#agents)). See the repository [README](../README.md) for an overview, and [docs/beta.md](docs/beta.md) for the guide for testers.

| Subpackage | Job |
| --- | --- |
| `capture` | The hook script, its installer and the git hook chain. Agents call the script on events: it appends one line to a per-session spool, hands the agent any note waiting for that event, and exits. Silent and fail-open; built-in modules only, so it starts fast. In git's pre-push it prints the push line, and never blocks a push. |
| `coordinator` | One process per user and environment, started by a hook when it is not running. It holds a lock (only one runs), reads the spools, owns the local record (SQLite), keeps each session's lifecycle, and exits when idle. It also stores the lines `orch label`, `orch missed`, `orch claim`, `orch release` and the MCP tools `declare`, `claim` and `release` append to its own spool, ends claims when they expire or their session ends, and brings a record of an older schema up to date when it opens it. A hooked session whose edits land in another worktree of its repository moves there with them. It runs the live map, the engine and the overlap rules, and writes each note in advance. It looks at the worktrees without a hooked session every `level0_seconds` (5) while they change, and less often while they stay the same, down to once a minute; each pass looks at a share of them (about half a second's worth), so a new session is recorded within about a second however many worktrees a repository has. |
| `livemap` | For each live session, the files it has changed since its base commit (from its edit events and git, after each tool call and every few seconds) and, for Python, the functions and classes added, removed, moved or modified, with each signature change rated breaking, review or compatible, and for a breaking change, which calls it breaks (a renamed parameter breaks only the calls that pass it by name). Worktrees with changes and no hooked session are followed as plain-git sessions, so agents without hooks, editors and people are seen too. Cloud agents' branches are followed the same way, read from a shadow repository's objects (see [Cloud agents' branches](#cloud-agents-branches-level-0)). Parses are cached by content and shared by every worktree; the engine's index of each base commit is built in the background and gives each session a code graph of its own copy of the code. Each session's HTTP routes are compared with its base commit's: added, removed, or with a changed method or path (see [HTTP routes and rule O5](#http-routes-and-rule-o5)). Where TypeScript contracts are on for the repository, so is the exported API of each session's TypeScript modules, from the compiler's declarations or, when the project does not compile, from their source (see [TypeScript contracts](#typescript-contracts-opt-in)). A changed Python file that does not parse (one caught mid-edit), cannot be read, or is over 2 MB is not compared until it reads whole again: it counts as the session's copy last showed it, else as its base commit has it, so none of its functions looks removed, and `orch status` lists it. |
| `rules` | The overlap rules for Python: O1 the same file (weak), O2 the same function (medium), O3 a breaking change used in a file another session is changing, O4 a removed function still used there, O5 an HTTP route both changed (its method and path: each added, removed it, or changed its method or path), O6 callers left behind that no session has updated (all strong). Uses come from the engine's resolved calls and inheritance, never from names alone, and count only when the change can break them, judged by how each call passes its arguments. A file in the other session's copy that uses the change but that it is not changing yet gives a latent finding: not listed as an overlap, but the session gets its note before its first edit of that file. W1 (medium): two sessions with hooks work in the same worktree, whichever subfolder each started in. O7 (medium): the work two sessions declared (the MCP tool `declare`) or claimed (`orch claim`) overlaps: a path covers the files below it, and two functions overlap only when they are the same. Between two sessions in one folder, O1 runs on the files each edited, and O2 to O5 do not, since what each did to a function cannot be told apart there. For TypeScript (`orch ts on`), O3 and O4 are medium, never strong: a use needs import evidence and calls are not resolved; O6 does not run for it. Each finding has a stable key; the coordinator opens, refreshes and resolves them. |
| `delivery` | Notes from templates over structured fields only (identifiers are cleaned, so no session's words reach another), written in advance into slot files for each receiving session and taken by the hook exactly once: before an edit of a file that uses a broken or removed function (O3, O4), with the next tool result (O2, O5, and who uses what you changed), at the end of a turn for callers left behind (O6), with the next tool result for another session working in this same folder (W1: one note per session per other session, which only informs, in steer mode too), and with the next tool result when the work two sessions declared or claimed overlaps (O7: one note to each, which only informs). Claims reach the other sessions before they edit what is claimed; see [Claims](#claims). One note per finding per session; a note whose finding stops holding before it is taken is withdrawn. A note about TypeScript says it is heuristic: calls not resolved. Also the push line, which stays for a worktree an agent has left (its changes are then followed as plain git), and the opt-in steer (only for a strong finding's note) and wake. |
| `mcp` | The MCP server, `orch mcp` (integration level 1): JSON-RPC 2.0 over stdio, standard library only. Its tools answer from the record, read-only: `who_is_changing`, `check_before_edit` (in the notes' own words), `my_overlaps`, `status`; and `declare`, `claim` and `release`, which append a line for the coordinator to store. See [MCP tools](#mcp-tools-level-1). |
| `adapters` | One per agent: Claude Code, Codex and Antigravity. Each declares its hook events (mapped to the common ones), the fields the hook script reads from them, its edit tools, the output each event hands a note back in, what it cannot be told, and the writer of its hooks file. The hook script keeps its own copy of what it reads and prints, and a test checks the two agree. See [Agents](#agents). |
| `ui` | The dashboard, `orch ui`: a page served on 127.0.0.1 that shows the state folder full screen. Read-only toward the record (opened read-only for each request); the steer and wake switches go through the same code as `orch config`. Standard library only, with no build step, and the page makes no request beyond its own server. Also the sandbox demo, `orch ui --demo`. |

## Commands

| Command | What it does |
| --- | --- |
| `orch init` | Copies the hook script into the state folder and adds hook entries for Claude Code's events to your user settings (`~/.claude/settings.json`, or the folder `CLAUDE_CONFIG_DIR` names), so every session and worktree is seen; then watches the repository it runs in and offers the push line (a pre-push hook chained in front of the repository's own hooks, which keep running, ones added to that folder later included; each hook git runs then starts a shell first, so on Windows a `git commit` took about 105 ms more, about 170 ms against 65 with git 2.53, and a checkout about 25 ms more). A relative `core.hooksPath` (husky's `.husky/_`) stays relative, so each worktree runs its own copy; one set for a single worktree (`git config --worktree`) is refused, as the push line would not run there. Run again in a repository with the push line, it writes it again with this state folder's hook script, rebuilds its folder if that is gone, and leaves any file it did not write there (a hook manager's) as it is. Shows what will change and asks first; `--yes` skips the questions, `--no-git-hooks` the push line, `--project` uses this folder's `.claude/settings.local.json` (and offers to keep it out of git through `.git/info/exclude`), `--claude-config DIR` another config folder, `--print` only prints the entries. The settings file is backed up before every change. With [Orchestraty's Claude Code plugin](#the-claude-code-plugin) installed, it adds no hooks to the settings file (it takes out any an earlier `orch init` added) and turns the plugin's hooks on instead, and says so. `--agent codex` or `--agent antigravity` installs into that agent instead (see [Agents](#agents)). `--python PATH` sets the interpreter the hooks run: orch init runs it once and refuses one that is not Python 3.10 or later (an empty value too). Hooks (and the mod) that an `orch init` with another state folder (`ORCH_HOME`) added are taken out, and it says so first. A settings file it cannot write (read-only, or open in another program) is refused with exit code 2 and left as it was. It also asks once whether to follow every project an agent works in (`watch_all` in `config.json`; `orch config track on\|off` changes it later), and offers to set up Codex and Antigravity when their folders are on this computer (`--yes` agrees for Claude Code and for following every project; it only names the other agents, and changes their files only when asked). It runs from any folder: no repository is needed. |
| `orch restore` | Removes Orchestraty's hook entries and leaves everything else, and turns the [plugin's](#the-claude-code-plugin) hooks off. `--from-backup` puts back the settings file as it was before the last `orch init`, but for the hooks (and the mod) of another state folder that `orch init` took out, which would fail once that folder is deleted; it says so when it leaves them out. `--agent` as for `orch init`. |
| `orch uninstall [--keep-state] [--yes]` | Takes out everything Orchestraty added: every agent's hook entries (in every file `orch init` wrote), the mod, the [plugin's](#the-claude-code-plugin) hooks and the plugin itself (with `claude plugin uninstall`, when the `claude` command is on the PATH; otherwise it says what to run), the lines `orch init --project` added to `.git/info/exclude` (the file goes back byte for byte where nothing else in it changed, and one `orch init` made is deleted), the push line in every watched repository and the cloud branches' shadows; then, after asking, the state folder. It prints all of it first and asks once. Where a settings file, without Orchestraty's entries, is as it was before `orch init`, the backup from then is put back byte for byte; where it changed since, only Orchestraty's entries come out, unless you say to put the backup back. Entries that are not Orchestraty's stay, and a second run changes nothing. `--keep-state` keeps the state folder (the record, the backups, the settings); `--yes` asks nothing, and keeps a file's changes since `orch init`. Orchestraty registers its MCP server with no agent itself, so a registration you made by hand stays, and it says how to remove it. The `orch` command stays too: `pipx uninstall orchestraty` removes it. The hooks of another state folder in the same files come out too. If a step cannot be done, or a settings file still runs the hook script (one it could not write, or a link it leaves alone), the state folder is kept so those hooks keep working, it says why, and the exit code is 1 (with `--keep-state` too): run it again once that is fixed. A coordinator that does not stop keeps the folder too. |
| `orch watch [PATH]`, `orch unwatch [PATH]` | Start or stop comparing the sessions of the project holding PATH (default: here): a git repository, or a folder without git (a folder project, followed through Orchestraty's own snapshots in `<state>/folders/`, never written into; not the home folder, a drive's top folder or the state folder). With `watch_all` on, every project an agent works in is watched without this, `orch unwatch` leaves one out (`exclude` in `config.json`) and `orch watch` takes it back. `orch init` watches the repository it runs in. Sessions in other projects are not compared, and nothing about them is recorded: while the coordinator runs, `orch status` and `orch ui` only name each such project an agent session works in, and how many sessions, so you can watch it (`orch ui` has a Watch button). A session that starts outside a watched project, in a parent folder say, counts from its first step in one. |
| `orch doctor [--no-index]` | Checks what Orchestraty needs and prints a fix for each problem: the Python (3.10 or later), the state folder (files can be made and deleted in it, and it is not in a folder OneDrive, Dropbox, Google Drive or iCloud Drive syncs), the record (that SQLite opens and reads all of it, and that it is not read-only; a damaged one gets 'move it aside'), the hook script, each agent's hooks (for Claude Code, which setup runs them: the settings file or the plugin; and none of another state folder's in the same file), that the coordinator starts with what a hook starts it with, the interpreter and import path in `hooks/launch.txt` (one doctor starts is stopped again, and one that fails leaves the hooks free to start the next), git (2.38 or later for the together check), in a repository with the push line a hook added to its hooks folder that git does not run yet, a hook script the push line runs that is not there (its state folder moved or deleted) and a push line folder that is gone (`orch init` again in that repository fixes each), and that the engine imports; in a repository it also times the first index, the engine reading every file at HEAD with no cache, which comes before the first note. The exit code is 1 when there is a problem. `--no-index` skips the timing. |
| `orch status` | The coordinator and the live sessions on each watched repository: agent, worktree, branch, base commit, last event, working or idle, what each has changed (files, and the functions whose contract changed), declared and claimed, the overlaps between them, strongest first, and merge-order advice. `--json` for other tools (the `schema` field versions it; every field is in [docs/status-json.md](docs/status-json.md)), `--all` to include ended sessions and latent overlaps. While the coordinator runs, it also names each repository an agent session works in that is not watched, with the `orch watch` that adds it. |
| `orch findings` | The findings seen in the last days, the latest first: rule, strength, what it is about, the sessions involved, first and last seen, open or resolved, and your label. Each has a short number that `orch label` takes for 24 hours (kept in the state folder's `finding-numbers.json`). `--all` adds the resolved and latent ones, `--days N` (default 7), `--json` for other tools. Reads the record without changing it. |
| `orch label <number\|key> real\|harmless\|false [--why "..."]` | Your verdict on a finding: real, harmless or false, with your reason if you give one. |
| `orch missed "<what should have been noted>" [--session ID]` | Reports a note that should have come; `--session` takes a session's id or its first characters. |
| `orch stats [--days 7] [--json]` | How Orchestraty was used, week by week, from the record (see [Measuring daily use](#measuring-daily-use)). `--json` carries a schema number. `--summary [--out FILE]` gives an anonymous summary: counts only, shown before it is saved. |
| `orch feedback [--out FILE] [--days 14] [--comment "..."]` | Your feedback: the `orch stats --summary` counts for the last `--days` days and your own comment, typed at a prompt (an empty line ends it). It prints all of it, saves it only to the file `--out` names once you say yes (`--yes` skips the question), and sends nothing anywhere: sharing it is up to you. |
| `orch claim <target> [--hard] [--for 2h] [--session ID]` | Reserves a file, a folder or a Python function or class (`path::name`, or `module.name`, resolved through the engine) for a session: by default the live session in this worktree, and when several work here it asks which; `--session` takes a session's id or its first characters. Other sessions are told before they edit there; `--hard` makes their edit wait for their user's answer, where their agent can ask. It holds for `--for` (`30m`, `2h`, `1h30m`, up to `24h`; by default `claim_minutes`, 120, in `config.json`). See [Claims](#claims). |
| `orch claims` | The claims that hold in each watched repository, with their numbers. Reads the record without changing it. |
| `orch release <number\|target>` | Ends a claim before it expires: the one with that number, or every claim on that file, folder or function in this repository. |
| `orch handoff [--session ID] [--task "..."] [--tests "<command>"] [--out FILE]` | Packages a session's work for another agent: by default the session working in this worktree. See [Handoffs](#handoffs-resume-and-merge-order). Prints the packet's id. |
| `orch resume <id> --agent claude\|codex\|antigravity\|"<command>" [--worktree PATH] [--dry-run] [--yes]` | Makes a worktree on a new branch from a handoff's head and starts that agent there, in your terminal, with the packet as its first message. Says exactly what will run and asks first. |
| `orch merge-order` | Which session's branch to merge first, from the findings; `orch status` shows the same lines. |
| `orch mcp [--folder DIR]` | Orchestraty's MCP server over stdio, for an agent to start in its workspace folder (see [MCP tools](#mcp-tools-level-1)). |
| `orch mcp --config claude\|codex\|antigravity` | Prints how to register the server with that agent, and the line to add to a repository's AGENTS.md so the agent calls `check_before_edit` before it edits shared code. Writes nothing. |
| `orch events [--follow\|--once] [--json] [--since TS]` | The record's changes, in the order it learned of them: sessions started and ended, findings opened and resolved, notes written, delivered and withdrawn, declarations, and claims made and ended. `--once` (the default) prints them and ends; `--follow` then polls about once a second for new ones, from now on or from `--since` (an ISO 8601 time, seconds since the epoch, or a time ago such as `2h`). `--json` prints one object per line ([docs/events-json.md](docs/events-json.md)). Reads the record without changing it. |
| `orch remote on\|off [--remote NAME]` | Cloud agents' branches for the repository here: fetched read-only and compared with your sessions (see [Cloud agents' branches](#cloud-agents-branches-level-0)). Off by default; `on` says what it will do and asks first (`--yes` skips the question). `--repo DIR` names another repository. |
| `orch remote patterns [add\|remove GLOB]` | The branches followed: by default `claude/*`, `codex/*` and `copilot/*`. |
| `orch remote fetch` | Fetches now, and says how it went. `orch remote` alone shows the settings and the last fetch. |
| `orch together [on\|off]`, `orch together set "<command>" [--timeout 120]` | The together check, for the repository here (`--repo DIR` names another): off by default. See [The together check](#the-together-check-opt-in). `orch together` alone shows the settings. |
| `orch ts [on\|off] [--timeout 300]` | TypeScript contracts, for the repository here (`--repo DIR` names another): off by default, since they run the project's compiler. See [TypeScript contracts](#typescript-contracts-opt-in). `orch ts` alone shows the settings and each session's latest run. |
| `orch config [steer\|wake\|track] [on\|off]` | Off by default. **track**: follow every project an agent works in (`watch_all`), git or not; `orch init` asks for it. **steer**: a strong finding's note before an edit (O3 or O4 about Python) stops that edit with the reason, so the agent re-plans (otherwise the note only informs, and the agent's usual permission prompts apply). **wake**: a note for a session that waits for its user wakes it (adds a background hook). |
| `orch ui` | The dashboard, in your browser: the sessions on each watched repository and what each has changed (files, and functions and classes with their contract changes), the overlaps between them grouped strong, medium and weak, each session's notes and events, every note with its time to awareness, the push lines, and the steer and wake switches. A Projects page lists every project, git or not, with its sessions and overlaps; the switcher at the top picks one. Local only: it listens on 127.0.0.1, at one address, port 47392 (a free one when something else holds it, or `--port N`); run again from any folder while one is running, it makes a new one-time link to that one (a token file in the state folder, taken once) and opens it instead of starting another, and prints a link with a one-time token, which it opens in your browser (`--no-browser` only prints it). Runs until Ctrl+C. `--demo` runs a sandbox instead: a temporary folder with a state folder of its own, a small repository with two worktrees and two pretend Claude Code sessions, driven step by step from the page through the real hook script, from a breaking change to its note, the push line and the overlap resolving. Nothing outside that folder is touched, and the folder is removed when it stops. The top bar's Refresh has the coordinator look at every worktree again at once; a repository agent sessions work in that is not watched gets a card with a Watch button, which does what `orch watch` does. |
| `orch coordinator run`, `orch coordinator stop` | For debugging: hooks start the coordinator when it is needed, and it exits after ten minutes with nothing to do. One that cannot open its record (not a database, damaged, a folder, no access) says why in `coordinator.log` and exits 6 (4 for a newer record's); one whose record opens but then fails 20 steps in a row (read-only, a full disk) exits 5. Either way the hooks then start none for a minute. |

The hooks record event names, session ids, folders and the paths of edited files; never prompts, file contents, commands or tool output. Nothing leaves the machine. `orch label`, `orch missed`, `orch claim`, `orch release` and the MCP tools `declare`, `claim` and `release` never write the record themselves: each appends one line to Orchestraty's own spool (`<state>/spool/orch/`), and the coordinator stores it. Your words (`--why`, the missed text) stay in the record on this machine and are never put into a note. When a session ends, its waiting notes are taken back. `orch unwatch` also takes the push line out of that repository's git hooks.

## Agents

| Agent | Hooks file `orch init` writes | Notes it can take | Another session's hard claim | Status |
| --- | --- | --- | --- | --- |
| Claude Code | `~/.claude/settings.json` (`--project`: `.claude/settings.local.json`) | before an edit, with the next tool result, at the end of a turn, and woken (wake on) | the edit waits for your answer | Capture test passed |
| Codex | `hooks.json` in its home folder (`CODEX_HOME`, by default `~/.codex`) | before an edit, with the next tool result, at the end of a turn | only informs | Built; not yet tested with the real agent |
| Antigravity | `~/.gemini/config/hooks.json` (`--project`: the workspace's `.agents/hooks.json`) | with its next step, at the end of a turn | only informs, once it has changed what is claimed | Built; not yet tested with the real agent |

Codex and Antigravity run each hook's command through a shell (on Windows a path that needs quoting is written in its short 8.3 form, which cmd and PowerShell both read; on a volume with no short names it goes in double quotes, which PowerShell reads, and cmd too when the agent passes the line to it as it is; only when the interpreter's own path needs quoting, or a path holds `%`, `$` or a backtick, is the line PowerShell's). The hook script reads each agent's own payload at byte level and writes the same spool line for all three. The tests replay synthetic payloads of each agent through the real hook script and measure its time for each: about 10 ms over a bare Python start on a Linux machine, the same for each agent.

**Codex.** `orch init --agent codex` merges its entries into the hooks already in `hooks.json`, for seven events: SessionStart, SessionEnd, UserPromptSubmit, PreToolUse (its edit tool, apply_patch), PostToolUse, Stop and SubagentStop. Codex runs a hook only after you have reviewed and trusted it: open Codex and run `/hooks`. Orchestraty never writes that trust, nor anything else in Codex's `config.toml`. The files an apply_patch changes are read from the patch's own lines. Notes come in the forms Codex reads: `additionalContext` before an edit and with the next tool result, and at the end of a turn a `block` decision whose reason keeps the turn going. Codex cannot be woken by a note, and its hooks cannot make an edit wait for your answer (Codex takes only deny as a PreToolUse decision), so another session's hard claim only informs a Codex session. Since Codex 0.157 the hooks of every Codex session on a machine run in one shared background process, with the environment and folder of the session that started it; so each event is placed by its payload's `session_id` and `cwd`, which every Codex hook event carries. Should a payload ever lack them, run Codex without the shared process: `daemon_auto_start = false` under `[features]` in its `config.toml`, or `codex --no-daemon`.

**Antigravity.** `orch init --agent antigravity` adds a hook named `orchestraty` to your user `hooks.json` for SessionStart, PreInvocation (before each call of its model), PostToolUse and Stop; other hooks there are kept. With `--project` it writes the workspace's `.agents/hooks.json` instead: a file inside your repository, so it shows it and asks first, offers to keep it out of git through `.git/info/exclude`, and never commits it. Notes come with its next step (PreInvocation, as an `ephemeralMessage`) and at the end of a turn (Stop, a `continue` decision whose reason keeps it going). Antigravity cannot take a note before an edit: its PreToolUse hook can only allow or deny the tool, so a note about a file comes with its next step once it has changed that file, and none comes about a file it is not changing. So PreToolUse is not hooked: there is nothing to tell it there, and Antigravity waits for that hook's answer before the tool runs. If it is hooked anyway, the hook answers `{"decision":"allow"}`. It cannot be woken by a note either, and another session's hard claim only informs it, with its next step once it has changed what is claimed. It has no session-end event: a session ends when no event has come for the session timeout. `orch status` shows each session's agent, and says what an agent there cannot be told.

## Measuring daily use

`orch stats` counts, for each week of the last `--days` days (the latest 7 days, the 7 before them, and so on):

- the sessions live in it (agent sessions with hooks, and plain-git ones), and the pairs of agent sessions on one repository working at the same time;
- the findings first seen in it, by rule and by strength (latent ones apart);
- the notes made in it, by kind (`edit`, `next`, `stop`, `wake`) and by state (`pending`, `written`, `delivered`, `withdrawn`), how many were delivered, and the median and 90th percentile of their time to awareness: from the event that caused a note to the note written, ready for its agent;
- the notes acted on, and the findings they were about;
- notes per session per day: the notes handed to agents over the days agent sessions were live (each day is 24 hours counted back from now), on average and on the busiest day;
- what was held back: weak findings, which no session hears (they show only in `orch status`), latent findings (nobody is changing the file that uses the change), notes a session did not get because it had heard of that finding already, and notes withdrawn because their finding stopped holding before the agent took them;
- the labels given in it, by verdict (a finding's latest label), and the reports of missed notes;
- an estimate of the tokens the notes handed to agents cost: their characters / 4.

Notes about claims (see [Claims](#claims)) count with the others; having no finding, they never count as acted on.

The hook's own time is not counted: the hook would have to read the clock and write it down on every event, which is work it must not do, and most of its time, the interpreter starting, passes before any of its code runs. The tests measure it from outside instead (see [Agents](#agents)).

**Acted on is a proxy**, worked out from the record only. A note handed to its agent counts as acted on when, within `acted_minutes` of its delivery (30 by default; set it in `config.json`), either the receiving session edited a file the note cites (the file its finding names, or one holding a function it names), or the finding stopped holding while that session was live. It says the agent did something the note may have caused, not that the note caused it.

`orch stats --summary` keeps counts only: no path, name, symbol, session id, date or text of yours. It prints first, so you read all of it; `--out FILE` then saves it once you say yes (`--yes` skips the question). Orchestraty never sends it anywhere. `orch feedback` is the same summary (for 14 days by default) with your own comment added as you typed it.

## MCP tools (level 1)

`orch mcp` is an MCP server over stdio for agents that support MCP: an agent can ask who is changing a file or function before it edits, say what it is about to change, and claim what other sessions must leave to it. It depends on the model remembering to ask; with hooks (level 2) the notes come without asking.

`orch mcp --config claude`, `codex` or `antigravity` prints how to register it with that agent (the `claude mcp add` or `codex mcp add` command, or the config snippet) and the line to add to your repository's AGENTS.md so the agent calls `check_before_edit` before it edits shared code. It writes nothing. **Tested with Claude Code,** whose agent called the server's tools in a real session; not yet with Codex or Antigravity. The tests drive the server over stdin and stdout as an agent does.

| Tool | What it answers |
| --- | --- |
| `who_is_changing(path, symbol?)` | The live sessions changing that file or function, or that have declared it, from any agent: each one's agent, worktree, branch, last event, and its function and contract changes with their reasons. A function's full id (path::name) names its own file. |
| `check_before_edit(path)` | What to know before editing the file, in the notes' own words: breaking or removed functions from other sessions that it uses, functions in it that another session is also changing, another session working in this same folder, and other sessions' claims on it. |
| `my_overlaps()` | The findings that involve the caller's session, strongest first, each with what it tells the caller. |
| `status()` | The caller's repository, as `orch status --json` has it. |
| `declare(paths, symbols?, task?)` | What the agent says it is about to change: files or folders of its worktree (or a new one in a folder that is there), with no spaces or control characters, and functions or classes by name (Class.method) or path::name. Anything else is refused, and the coordinator drops a declaration of any other shape. Other agents see the paths and functions cleaned as notes clean them; `orch status` shows the task line with its control characters taken out. |
| `claim(target, hard?, minutes?)` | Claims a file, a folder or a function or class (`path::name`, or `module.name`) for the caller's session, as `orch claim` does. |
| `release(target)` | Ends one of the caller's own claims: what it claims, or its number. Another session's claim stays. |

Each answer is structured JSON and a short text that says what it covers and what was not analysed, the way notes do. Identifiers are cleaned, and no session's words reach another.

**The caller's session.** An agent starts the server in its workspace folder. That folder is `--folder DIR` when given, else Claude Code's project folder (`CLAUDE_PROJECT_DIR`) when it sets one, else the folder the server starts in. The caller's session is the live session working in that folder's worktree, one with hooks before a plain-git one. Claude Code starts the server of a desktop-app worktree session (and of a session that entered a worktree with EnterWorktree) in the main checkout, and puts those worktrees under the main checkout's `.claude/worktrees`, so the server answers for the sessions working in its own worktree or in a worktree inside it. When more than one session with hooks works there, `check_before_edit`, `my_overlaps`, `declare`, `claim` and `release` ask for their optional `session` argument: the absolute path of the folder the agent works in, or its session's id (or the id's first characters, as `orch status` shows them); they never guess. Naming a session outside those worktrees is refused, so an agent cannot end another session's claim, claim or declare in its name, or read its task line. Within them the server cannot tell its callers apart: an agent there could name another of those sessions, as two sessions in one worktree could (W1 already tells those to separate). A server started outside any worktree takes the worktree from the absolute path a tool is given, or from `session`, for the tools that read; it returns no task line and refuses `declare`, `claim` and `release` (start it with `--folder`). This binds what an agent can do through its MCP tools, not what someone with a shell can do: `orch` acts on any session, because it is yours. An agent without hooks has a session once its worktree has changes (a plain-git session); until then `who_is_changing`, `check_before_edit` and `status` answer, and `my_overlaps` and `declare` say why they cannot.

**Declarations.** The server never writes the record: `declare` appends one line to Orchestraty's own spool, and the coordinator stores it. A declaration holds for `declare_minutes` (120 by default, in `config.json`). `orch status` shows the declarations that hold, with the agent's task line. Other agents see the paths and functions, in `who_is_changing` and `status`, and never the task line; no note carries it. Rule O7 compares what sessions declared and claimed: when two overlap, each hears once, with its next tool result.

**The protocol.** JSON-RPC 2.0, one message per line, in the MCP protocol versions 2024-11-05, 2025-03-26, 2025-06-18 and 2025-11-25 (a client asking for another gets the newest). The server answers `initialize`, `ping`, `tools/list` and `tools/call`, takes notifications without an answer, and answers anything else, and a call whose arguments do not fit the tool, with the JSON-RPC error for it. When a tool cannot answer, its result says why and is marked as an error. stdout carries protocol messages only; the server logs to stderr. It reads the record read-only and starts no coordinator, so its answers are as of the coordinator's last pass, and say whether it runs.

## Claims

A claim reserves part of a repository for one live session, so that every other session hears of it before it edits there. `orch claim payments.charge` claims the function `charge` in `payments.py`; `orch claim billing/` claims the folder `billing` and every file in it; `orch claim billing/refunds.py` claims one file. An agent claims through the MCP tool `claim`.

- **What a target is.** A file or a folder, absolute or relative to where the command runs; or a Python function or class, as `path::Qualified.name` or `module.name`, resolved through the engine to the file that defines it. Claims are kept in canonical form: a path from the top of the repository, and `path::Qualified.name` for a function or class. The whole repository cannot be claimed.
- **The record.** `orch claim` and the MCP tool append a line to Orchestraty's own spool, and the coordinator stores the claim in the record (schema 4), so it survives a coordinator restart. It holds until it expires, until it is released (`orch release`, the MCP tool `release`), or until its session ends. `orch status`, `status.json` (which the mod reads) and `orch claims` show the claims that hold; `orch events` shows each one made and ended.
- **What other sessions hear.** Each other live session with hooks on the repository gets one note per claim, written in advance into its pre-edit slot: who claimed what, until when, and the claim's number. For a claimed function or class, the slot is that of the file that defines it; for a folder, a slot of the folder that the hook script takes before an edit of any file in it. A session that has already changed what is claimed also hears with its next tool result, unless its edits there are to wait for its user's answer. A claim that ends takes back its notes not yet taken.
- **Hard claims.** `--hard` (the MCP tool's `hard`) makes another session's edit there wait for its user's answer, where its agent can ask: for Claude Code, a PreToolUse permission decision of `ask`, with the note as the reason you see, and as context for Claude. Orchestraty never answers `allow`, which would skip your own permission prompt, and never denies silently. Codex and Antigravity hooks cannot make an edit wait for an answer, so their sessions are only informed, and the note and `orch status` say so. Steer never turns a claim's note into a deny.
- **Overlapping claims.** Two sessions whose claims or declarations overlap get rule O7: a medium finding, one note to each with the next tool result, and nothing held back.

Tested end to end with the real hook script for each agent's payloads; not yet with the real agents.

## Handoffs, resume and merge order

**`orch handoff`** packages a piece of work from the record and git, for another agent to take over: the task line, the branch, base commit and head, the files changed (and which of them were not committed, so are not in the head), the contract changes with their reasons, the open findings that involve the session, in the notes' words, and the callers it left behind. The task line is your `--task`, else the line the agent gave when it declared its work (the MCP tool `declare`), else the branch name: the hooks never store prompts, and a handoff never reads a prompt or a transcript. `--tests "<command>"` runs your command in the session's worktree, with a time limit (`--timeout`, 600 seconds by default) and without git's variables; its exit code and last lines go in the packet, marked as the command's own output. The packet is Markdown, with the same content as JSON beside it, in `<state>/handoffs/<id>.md` and `.json`; `--out FILE` writes a copy (never over an existing file).

**`orch resume <id> --agent ...`** is the one place Orchestraty starts an agent, and only when you run it. It makes a worktree on a new branch, `<branch>-<id>`, from the packet's head (beside the session's worktree, or at `--worktree`), then runs the agent's own command-line tool there, in the foreground, in your terminal, with the packet as its first message: `claude "<packet>"`, `codex "<packet>"` or `agy --prompt-interactive "<packet>"`; a command of your own gets the packet on its standard input. It prints exactly what will run and asks first (`--yes` skips the question, `--dry-run` only prints). Nothing else is passed: each agent keeps its own permissions and model settings, since one agent's permissions translated into another's would be unsafe, and nothing runs in the background. On Windows a tool installed as a `.cmd` or `.bat` file is run through cmd.exe, which cannot take a line break in an argument, so its first message is one line naming the packet's file. Tested with a stand-in agent that records what it is given; **not yet tested with the real agents**, and Antigravity's `--prompt-interactive` is taken from its changelog.

**Merge order.** From the open findings, the same way every time: when a session is changing a file that uses what another session changed in a way that breaks it, or removed (O3, O4, not latent), the other merges first: "merge refunds first: annual uses charge in billing.py, which refunds changed." When each uses what the other broke: "refunds and annual depend on each other (...): merge them together, or coordinate." Otherwise nothing is said. Sessions are named by their branch.

## HTTP routes and rule O5

The engine reads the HTTP routes of FastAPI, Flask and Django from the syntax tree, importing and running nothing (its README's [Routes](../engine/README.md#routes) lists what it reads): each route's method, its full path (the router, blueprint and `include()` prefixes it is mounted under, followed across files through the imports), its handler, file and line. A route is **exact** when every part of its path is a literal (a string, a name its module binds once to one, or `+` and f-strings of those) and its chain up to an app is known; otherwise it is **heuristic**, with the part that could not be worked out shown as `{?}`.

For each live session, the routes of its copy of the code are compared with its base commit's, once that commit's index is ready: a route removed, or whose method or path changed (one removed and one added with the same handler), is a breaking change of the contract; a new route is compatible. **O5** (strong): two live sessions in worktrees of their own both change the same route, its method and path, a changed route counting under both its old and its new one. Both sessions hear with their next tool result, from a template: which route, where it is declared, and what each did to it. A path is shown only when it is made of a path's characters and parameters, a parameter shown in braces (`/users/{uid}`; Flask's and Django's `/users/<int:uid>` as `/users/{int:uid}`); a regular expression's (Django `re_path`) or one with any other character is left out, and where it is declared says which route. Only exact routes count, on both sides: a heuristic route never makes O5. Not read: routes added by calls (`add_url_rule`, `add_api_route`), class-based routers such as Django REST framework's, and routes built in loops.

## The together check (opt-in)

Static rules are precise only where the engine understands the language well, so the together check confirms an overlap by running code. It is off by default, for each repository: `orch together set "<command>"` names the check to run, such as a type check or the tests that use the changed function, and `orch together on` turns it on. The settings are kept in Orchestraty's `config.json`, never in the repository.

When the rules flag a medium or strong overlap between two live sessions in worktrees of their own (O2 to O5, not latent), the coordinator queues a check of the pair: once per content state of the two working copies, at most once a minute for a pair, one check at a time, on a thread of its own, never in a hook, and never holding up the coordinator. A check:

- **snapshots** each session's working copy, its tracked files and the untracked files git does not ignore, as a commit whose parent is the session's base commit, written into a scratch object store in the state folder. git runs with `GIT_OBJECT_DIRECTORY` set to the scratch store, `GIT_ALTERNATE_OBJECT_DIRECTORIES` to the repository's objects and `GIT_INDEX_FILE` to a temporary index, so your index, refs and objects stay as they were: a test checks them byte for byte;
- **merges** the two snapshots with `git merge-tree --write-tree` (git 2.38 or later); a text conflict is reported as one, and nothing runs;
- **runs** your command, with its time limit (`--timeout`, 120 seconds by default) and no `GIT_` variable, on the merged tree and on each snapshot alone, each checked out into a folder of its own outside every repository (git there finds no repository, even when the state folder is inside one: `GIT_CEILING_DIRECTORIES` stops it at the check's folder; git splits that variable at `;` on Windows and `:` elsewhere, so this does not hold for a state folder whose path has one), so "fails together" is told apart from "already fails alone";
- **records** the exit codes and the last lines of output, in `<state>/together/results.json`, which `orch status` shows.

When each passes alone and they fail together, both sessions get one note with their next step: "each passes alone, your working copy and that of another Claude Code session (...); together `<command>` fails with TypeError at tests/test_a.py::test_x". The note names only the error and the test or file:line from the line of output that says the most; that line is the merged code's own output, which may hold another session's words, so `orch status` shows it to you and no note or MCP tool quotes it. The scratch store and the folders are removed when a check ends; what an interrupted check left is removed by the coordinator's housekeeping.

## TypeScript contracts (opt-in)

Comparing a TypeScript project's exported API with the compiler runs your toolchain, so it is off by default, for each repository: `orch ts on` turns it on for the repository here (`--timeout` sets how long one compiler run may take, 300 seconds by default), `orch ts off` turns it off, and `orch ts` alone shows the settings and each session's latest run, as `orch status` does. The settings are kept in Orchestraty's `config.json`, never in the repository.

When it is on, for a live session in a worktree of its own that changed `.ts`, `.tsx`, `.mts` or `.cts` files, the coordinator compares the exports of its TypeScript modules with its base commit's:

- **With the compiler**, where the worktree has a `tsconfig.json` at its top and a TypeScript compiler (`node_modules/.bin/tsc`, else `tsc` on PATH): the compiler writes the declarations (`--declaration --emitDeclarationOnly`) of the session's working copy, and of its base commit, into the state folder, each with an `--outDir` and an `--incremental` build-info of its own, so nothing is written into the repository; a test checks `git status`. The base commit's files are checked out into a folder of the state folder that borrows the worktree's `node_modules` through a link (a junction on Windows), read only; the link is removed afterwards, never what it points at. One run at a time, on a thread of its own, never in a hook, each with its time limit; a session is compiled again once its TypeScript files changed, at most every 15 seconds. A run counts as compiled when declarations were written and no error is about the project itself (its options, its inputs, its `tsconfig.json`): type errors in the code leave the declarations right. A config that sets `outFile` is not compiled.
- **The comparison** reads the declarations module by module, with a small `.d.ts` reader in Python (standard library). **Breaking**: an export removed; a parameter removed or made required; an overload removed; a property or method removed from an exported interface, object type or class; a required property added to an interface an exported function takes; an enum member removed. **Review**: a return type changed; a type narrowed, where it can be told (a union that lost members); a required property added to an interface not known to be an input. **Compatible**: an optional parameter, a new export, an optional property. A renamed parameter changes nothing, since calls pass it by position.
- **The fallback**, where there is no `tsconfig.json` at the top or no compiler, a side does not compile, or a run takes too long: the exports of the changed files are read from their source with the same reader (function bodies and initializers skipped, so a type not written there is not known), at the base commit and in the working copy, and compared the same way. What it finds is heuristic, and `orch status` says why it was used.

A file with a syntax error its base commit does not have, as one caught mid-edit, is not compared until it reads whole again: what the compiler declares for it is what it made of what it could read, which can make a later export look removed. With the compiler, that is a TS1xxx error in the file; in the fallback, brackets, template literals or comments left open. `orch status` lists such files.

**Uses** need import evidence. Each session's copy of the code (its base commit's TypeScript and JavaScript files, with its own changes) is read for its imports, resolved to files: relative paths (a `.js` specifier names the `.ts` file), a folder's `index`, and the `baseUrl` and `paths` aliases of the nearest `tsconfig.json` and the configs it `extends` by relative path. A use is a file that imports the export, directly or through up to three re-exports (`export { ... } from`, `export *`), and names it outside the import: by its local name, or as `namespace.name`. Which of those are calls, and what they pass, is not resolved. So for TypeScript, **O3** (a breaking change) and **O4** (a removed export) used in a file another session is changing are medium, never strong: the finding has `heuristic` set, the note says "heuristic: calls not resolved", and steer never stops an edit for it. O6 does not run for TypeScript, and the rules for Python are as they were.

Tested with the fixtures in `tests/` and TypeScript 5.9.3, which `tests/fixtures/ts/package-lock.json` pins and CI installs with `npm ci`, on Windows and Linux; not yet tested on a real project. Not read: the exports of JavaScript files (they are read for their imports only), a `tsconfig.json` other than the one at the worktree's top (a monorepo's packages get the fallback), and an `extends` that names a package, for aliases (the compiler still reads it).

## The stable JSON interface

For other tools, `orch status --json` ([docs/status-json.md](docs/status-json.md)) and `orch events --json` ([docs/events-json.md](docs/events-json.md)) each carry a `schema` number. Within one schema number, fields are only added: none is removed, renamed or changes its type or meaning.

## Cloud agents' branches (level 0)

Agents that work while you do, such as a cloud agent pushing a branch or a personal agent running coding tasks, are the likeliest to collide with you. With `orch remote on`, run inside a watched repository, Orchestraty fetches the branches they push and compares each one with your live sessions, through git alone (level 0). It is off by default, for each repository.

- **What is fetched:** from the remote (`origin` unless `--remote` names another), its default branch and the branches matching the patterns: by default `claude/*`, `codex/*` and `copilot/*`, the prefixes agents push to. `orch remote patterns add|remove GLOB` changes them; a pattern is a refspec glob, with one `*` at most.
- **Where it goes:** into a repository of Orchestraty's own in the state folder (`shadows/<key>.git`), under `refs/orch/<remote>/`. It is a bare repository that reads your repository's objects (`objects/info/alternates`), so a fetch downloads only what yours lacks. Nothing is written into your `.git`: a test checks that its refs, packed-refs, index, config and objects are byte for byte the same.
- **When:** every 5 minutes while the coordinator runs (`remote_fetch_minutes` in `config.json`), on a thread of its own, and when you run `orch remote fetch`. This is the one place Orchestraty uses the network. git runs with no terminal prompt and no askpass, ssh in batch mode, and a two-minute timeout: without credentials a fetch fails rather than asks. A failure is kept and shown in `orch status`, and the wait before the next try doubles each time, up to an hour. If your garbage collection removes an object the shadow relied on, the shadow is fetched afresh.
- **Sessions:** each matching branch is a session of agent `cloud`, named `<remote>/<branch>`. It is based on the branch's merge base with the remote's default branch, and its changes, files and Python functions alike, are read from the shadow, base to tip, by the same live map and engine. It ends when the branch is deleted, or merged into the default branch (a squash merge counts once the branch is deleted).
- **Notes:** the rules run as for any session, and notes go to your live sessions: a breaking change on a cloud branch, used in a file one of them is changing, gives that session its note before it edits the file. The branch's own agent works elsewhere and is never told (level 0); the notes say so, and so does `orch status`, which shows the cloud branches in a group of their own: each branch, what it changed, its last commit's time, and the last fetch with its result.

Tested with local remotes; not yet with a real cloud agent's branch on a hosting service.

## For builders

An agent you build yourself gets what an agent with hooks gets (level 2) from calls in its own loop: one before it writes a file, one after, and one at the end of a turn. Two helpers make the calls, one for Python and one for TypeScript or JavaScript. Both go through the hook script `orch init` installs, so the spool lines, the notes and the coordinator are the ones every agent gets. Run `orch init` once, in the repository the agent works on: it installs that script and watches the repository.

| Python, `orchestraty.helper` | TypeScript, `helpers/typescript` (async) | Hook event | Returns |
| --- | --- | --- | --- |
| `Orchestraty(agent="mybot", cwd=worktree)` | `new Orchestraty({ agent: "mybot", cwd: worktree })` | | One session; a new id unless `session_id` (`sessionId`) is given. |
| `start()` | `start()` | SessionStart | Nothing. |
| `before_write(path)` | `beforeWrite(path)` | PreToolUse | The note waiting for this file: a function another session broke or removed that this file uses. Else None (null). |
| `after_write(path)` | `afterWrite(path)` | PostToolUse | Records the edit. The note waiting for the next step: another session is changing the same function, uses what this one changed, or works in this same folder. Else None (null). |
| `end_turn()` | `endTurn()` | Stop | The callers this session's changes left behind. Else None (null). |
| `end()` | `end()` | SessionEnd | Nothing; the session's waiting notes are taken back. |

A note comes back as its text. The agent shows in `orch status` as `helper-<name>` (letters, digits, `-` and `_` of the name are kept). A call never raises: on any error it returns None (resolves to null), the way the hook fails open.

- **Python.** By default the hook's code runs in the agent's process: the helper loads the installed script and calls its functions, as the script's own main() does, so a call starts no interpreter (about 0.1 ms on Linux). `in_process=False` runs the script as a process instead, the way an agent runs a hook (about 20 ms on Linux). A test checks that both write the same bytes for every event and take slots the same way.
- **TypeScript.** Node 18 or later, no runtime dependencies, not published: `npm ci && npm run build` in `helpers/typescript`, then import it from there. Each call runs the script as a process, with the interpreter `orch init` recorded in `<state>/hooks/launch.txt` (about 20 ms on Linux). It finds the state folder as `orch` does, and a test checks that it writes the same lines as the Python helper. See its [README](../helpers/typescript/README.md).

[`examples/homemade-agent`](../examples/homemade-agent/) is an agent with no model that uses the Python helper for two sessions in two worktrees: the session about to edit a caller hears of the other session's breaking change from `before_write` before it writes. A test runs it with the installed hook script and a coordinator the hook starts.

## The Claude Code mod

`orch init` also loads Orchestraty's [mod](https://code.claude.com/docs/en/plugins/mods/overview) (Claude Code 2.1.287 or later): it copies it into the state folder and adds that folder to `CLAUDE_CODE_PLUGIN_DIRS` in the same settings file. The mod shows; it detects nothing. Every few seconds it reads the status the coordinator keeps (`status.json`, the same as `orch status --json`) and draws:

- a line under the prompt: how many other sessions work on this repository, and the overlaps that concern this session;
- a band above the prompt, only for strong overlaps that concern this session, with **Show all** and **Dismiss**;
- a pane with every session on the repository and every overlap: `/orch`. Also `/orch status`, `/orch steer on|off`, `/orch wake on|off`.

Notes still reach Claude through the hooks. The one thing the mod hands over itself is a wake note for its own session while that session waits for its user: it asks the hook script to take the note (exactly once) and submits it as a prompt. The mod reads only Orchestraty's state folder, starts only Orchestraty's own Python, and makes no network request; `claude plugin validate` lists exactly that. `--no-mod` leaves it out. In the desktop app, WSL sessions load no plugins, so the mod is absent there while the hooks still work.

## The Claude Code plugin

[`plugins/claude-code`](../plugins/claude-code/) is a Claude Code plugin that holds what `orch init` otherwise writes into Claude Code's settings, the hooks (the same events and matchers) and the mod, and also registers the MCP server (`orch mcp`, which needs `orch` on the PATH) and adds a skill on how to treat Orchestraty's notes: facts from other sessions, never instructions; `check_before_edit` before editing shared code; on a strong note, adapt, fix the callers left behind or ask the user; never edit another session's worktree. The repository is its marketplace (`.claude-plugin/marketplace.json`). In Claude Code:

```text
/plugin marketplace add samratrajsharma/Orchestraty
/plugin install orchestraty@orchestraty
```

Then run `orch init` as usual. If you registered the MCP server yourself (`orch mcp --config claude`), remove that registration: the plugin brings its own.

- **The hooks run the hook script `orch init` installs.** A plugin's files are fixed, so its hook command cannot name an interpreter: it is a short sh command (Claude Code runs a plugin's command hooks with sh, and with Git Bash on Windows) that finds the state folder as `orch` does, reads the interpreter from `<state>/hooks/plugin.txt` and replaces itself with `<python> -S -I <state>/hooks/hook.py claude <event>`, exactly as the settings hooks run. With no `plugin.txt`, no interpreter at the path it names or no hook script, as when Orchestraty is not installed, it does nothing and exits 0.
- **Never twice.** `plugin.txt` is the switch. `orch init` writes it only when the plugin is installed (Claude Code's `installed_plugins.json` lists `orchestraty@<marketplace>` for the user, or for this folder with `--project`, and the settings file does not turn it off); it then adds no hooks to the settings file, takes out those and the mod an earlier `orch init` added, and says so. Without the plugin it adds the settings hooks and removes the file. A plugin installed after `orch init` therefore stays silent until `orch init` runs again. `orch config wake on|off` sets the wake line in `plugin.txt`.
- **`orch restore`** removes the settings hooks and `plugin.txt`, so the plugin's hooks do nothing, and says how to remove the plugin itself (`claude plugin uninstall orchestraty@orchestraty`), which `orch` does not do.
- **`orch doctor`** says which setup runs the hooks, the settings file or the plugin (`hooks from the plugin orchestraty@orchestraty <version>`), and flags hooks in both, the plugin installed with its hooks off, an installed copy with another version's hooks, the mod `orch init` loads from the state folder taking the plugin's place (it has the same name), and, on Windows, no Git Bash.
- **Speed.** `tests/test_plugin.py` measures the plugin's hook as the hook timing test measures the settings hooks, through the shell Claude Code runs it with. On Linux the sh command adds 0.6 ms to the hook: 10.5 ms in all over a Python that does nothing, against a budget of 30 ms. On Windows that shell is Git Bash, and its start puts the hook over the budget: 72.6 ms against 20.6 ms for a Python that does nothing, on a CI machine. No faster form fits a plugin there (only a hook that starts an interpreter named by its absolute path, as the settings hooks do, avoids a shell, and a plugin's files are the same on every machine), so on Windows the settings hooks are the faster setup: leave the plugin out, and `orch init` writes the hooks and the mod into the settings file, and `orch mcp --config claude` shows how to register the MCP server. `orch init` says so on Windows.
- **Built files.** `hooks/register.js` is the mod's module, copied, because a plugin may not point outside its own folder; `hooks/hooks.json` and the manifest are generated from the package. `python scripts/build_plugin.py` writes them, and a test fails when they differ.

Checked with `claude plugin validate --strict` (Claude Code 2.1.309). Installed from this repository's marketplace in a real Claude Code (2.1.292, in a profile of its own): its hooks delivered every note of a two-session test, and the agent used its MCP tools. Its mod and skill were not checked there, since the test ran without a screen.

## Where state lives

One folder per user and environment, never inside a repository: `%USERPROFILE%\.orchestraty` on Windows, `$XDG_STATE_HOME/orchestraty` (by default `~/.local/state/orchestraty`) elsewhere. `ORCH_HOME` overrides it; after changing it, run `orch init` again (for each agent): it moves the hooks to the new folder. Before you delete the old folder, also run `orch init` in each repository it watched, which moves the push line to the new folder (or `orch unwatch` there; `orch doctor` in such a repository says so); otherwise each `git push` there prints Python's "can't open file" for the old folder's hook script. Windows and each WSL distribution have their own folder.

## Rules

- Python 3.10 or later, standard library only in the core.
- May import the engine (`orch_engine`). The engine never imports this package. `tests/test_layout.py` checks it.
- Tests leave nothing behind in the working copy.

## Run the tests

```bash
cd orchestraty
python -m pytest
```

## Install for development

The distribution is `orchestraty`, one pure-Python wheel that holds this package and the engine (`orch_engine`); its `pyproject.toml` is at the repository's top. From there:

```bash
pip install -e .
orch --version
```

Both packages are then imported from where they are. From the repository's top folder, run `orch` rather than `python -m orchestraty`: there, Python finds the folder `orchestraty/` before the package. `scripts/smoke.py` tests a built wheel end to end, and `scripts/first_note_timing.py` times install to first note; the root README says more.
