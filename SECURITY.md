# Security

## Reporting a problem

Please report a security problem privately, not in a public issue: on this repository's **Security** tab, choose **Report a vulnerability** (GitHub's private vulnerability reporting). Say what you ran, what happened, and which version (`orch --version`). The maintainers answer in that report, and agree with you when the fix and the problem are made public.

Examples of what we treat as a security problem:

- one session's own words (a prompt, a comment, a string in its code) reaching a note for another session;
- anything leaving the machine without the user running a command that exports it;
- a write outside the state folder that the user did not agree to, or into a repository's tracked files;
- a hook that blocks, fails or slows an agent beyond what the docs say;
- prompts, file contents, commands or tool output stored anywhere;
- a teammate's record reaching an agent as anything but cleaned identifiers;
- a string leaving the machine that `orch team preview` does not show.

## What Orchestraty reads

- **Agents' hook events.** The hook script copies a few named fields from each event and nothing else: the session id, the event name, the working folder, the tool's name and call id, the path of the file an edit tool changes, the transcript's path (the transcript itself is never opened), and, for a few events, why the session started or ended. It reads only the event's own top-level fields (and the edit tool's own input fields: a Codex patch's header lines, Antigravity's toolCall name and file), finding them in the raw bytes without parsing the payload, so a field of the same name inside a tool's input or output is never taken for one. Prompts, file contents, commands and tool output are never stored.
- **The repositories you watch.** Through git, read-only: each session's changes against its base commit, and the code at that commit, which the engine parses to compare contracts. Sessions in repositories you don't watch are dropped unread.
- **Agents' settings files,** when you run `orch init`, `orch restore`, `orch uninstall`, `orch config wake` or `orch doctor`.
- **Its own state folder:** `%USERPROFILE%\.orchestraty` on Windows, `$XDG_STATE_HOME/orchestraty` (by default `~/.local/state/orchestraty`) elsewhere, or the folder `ORCH_HOME` names.

## What Orchestraty writes

- **The state folder:** the hooks' spool lines, the record (one SQLite file, written only by Orchestraty's background process), the notes waiting for each session, the status other tools read, the settings, backups of every agent file it changed, a copy of the hook script and of the Claude Code mod, handoff packets, and, when you turn them on, the cloud branches' shadow repositories and the together check's scratch copies (removed when each check ends); and, after `orch team on`, this machine's team device (`team/device.json`, readable by you only), a marker file while any repository has team sync on, and what team sync keeps beside a shadow repository.
- **Agents' settings files,** only when you run a command that changes them. It shows the change and asks first (`--yes` skips the question), backs the file up first, and leaves every entry that isn't its own as it was.
- **Inside a repository, only after showing and asking:** the push line, a pre-push hook chained in front of the repository's own (`core.hooksPath` set to a folder inside `.git`; `orch unwatch` and `orch uninstall` take it out and put back only a value the repository's own config had, never one from your global config; for a push line an earlier version added, which did not record where the value was set, only a relative value or one inside the repository; `orch init` run again rewrites only its own scripts in that folder); and, with `--project`, the agent's settings file in the workspace, with a line in `.git/info/exclude` to keep it out of git. `orch resume` makes the worktree and branch you ask it for. Orchestraty never commits to your branches and never pushes them. The one ref of its own it pushes is its team record ref, `refs/orchestraty/<you>/<device>`: only after you turned team sync on, only right after your own successful push to that remote, and with a lease, so it replaces only what this device last saw there; `orch team off --forget` deletes it (it asks first). On a host that refuses such refs (it hides them, or a hook says no), the record goes instead into one branch of Orchestraty's own, `orchestraty/records`, as the file `records/<you>/<device>.json`, each commit marked `[skip ci]` and the branch holding no project file; it never touches another branch.

`orch uninstall` takes all of it out again: see the [README](README.md).

## The network

- **The hooks, the background process, the Claude Code mod and the editor extension make no network calls.** The hook script imports no networking module, and the mod reads only Orchestraty's state folder and starts only Orchestraty's own Python.
- **The only network access is opt-in:** the cloud-branch fetch and team sync. After `orch remote on` (it says what it will do and asks first), Orchestraty fetches the branches of cloud agents (`claude/*` and the other patterns you keep) from your repository's own remote, read-only, into a shadow repository in the state folder, every few minutes. `orch remote off` stops it.
- **Team sync,** only after `orch team on`, which says what it reads and asks first: a read-only fetch of the team remote's default branch, for the policy and people file in force there, into the same shadow repository; and one anonymous-read probe, `git ls-remote --heads` of the remote's https address with no credentials, to catch a repository the policy calls private that anyone can read. From then on, while the coordinator runs: this device's record is pushed to its own ref right after your own successful push (git's reflog says when; a push git refused sends nothing), as a second connection that never prompts, runs no hook and signs nothing; and the remote's record refs and the branches records name are fetched into the shadow every two minutes, read-only. `orch team off` stops both, and `--forget` deletes this device's record ref there. No hook and no doctor run uses the network: git's pre-push hook only writes a line and may start the coordinator.
- **No telemetry.** `orch stats --summary` and `orch feedback` print what they hold, save it only where you say, and send nothing.
- Commands you set up yourself run as you set them: the together check runs the test command you give it (`orch together set`), `orch ts on` runs your project's TypeScript compiler, and `orch resume` starts the agent you name. The engine's own development tools (`python -m orch_engine.check`, its MCP server) can clone a repository you name by URL; `orch` never does.

## Notes cannot carry another session's words

Every note is filled in from a template with identifiers from git and the code graph (function, file and branch names, line numbers, an HTTP route's method and path), cleaned to a short list of safe characters (never a space, and never `<` or `>` but in a nested function's `<locals>`) and cut to a set length. A route's path appears only when it is made of a path's characters and parameters, a parameter shown in braces (`/users/{uid}`; Flask's `/users/<int:uid>` as `/users/{int:uid}`); any other path is left out, and the note says where the route is declared. Nothing another session wrote reaches a note, so one session cannot give another instructions through it. What an agent declares (the MCP tool `declare`) is held to the same: paths of its worktree and function or class names, never free text; its task line is shown only to you, to that agent, and to the agent you hand its work to with `orch handoff`. The MCP tools answer with the same cleaned names, `status` included, and a session id is only ever letters, digits, `-` and `_` (the coordinator drops an event whose id is anything else). The together check's note names only the error and where it happened (`TypeError`, `tests/test_a.py::test_x`): the line of output it failed with was printed by the merged code, so it may hold another session's words. `orch status`, `orch findings` and the dashboard are your own view: they show names, task lines and that line as they are, without their control characters, so an agent that runs `orch status` in its shell reads them too; no note or tool points an agent at it.

Orchestraty never answers an agent's permission question with "allow". With steer on (off by default), a strong finding's note stops the edit it is about; a hard claim makes another session's edit wait for its user's answer. A teammate's claim does neither: it only informs, since a remote item may be stale or forged.

## Between teammates

Team sync shares, through the repository's own remote, a small record of the sessions on this machine, as the repository's policy (`.orchestraty/policy.yml` on its default branch) allows and only after `orch team on`. It goes to one ref per device, `refs/orchestraty/<you>/<device>`, each record a commit holding only `record.json`, made in the shadow repository (never in yours), named by your handle and git email and dated in UTC. A plain `git fetch` or `git clone` of the repository does not bring these refs, and your own `git push` never pushes them.

- **The record is closed.** Each field has a fixed grammar: agent kind, state and times in minutes, branch, base and pushed commit, a ticket, a task line its author confirmed, claims, and only where the policy says so the files and functions of committed but unpushed work. There is no field for a prompt, a transcript, file contents, a path outside the repository, a host name, an email or a commit message, and a session goes under an id made with a secret that never leaves the machine, never the agent's own.
- **One gate out.** The effective policy (the most restrictive of the copy in force, the copy you agreed to and your own narrowing) drops what it does not share; every field must follow its grammar; a path the built-in list or the policy denies, and any text with a word the policy denies, is withheld; a secret scanner (token formats of known providers, private key headers, credentials in a URL, password-style assignments, long random-looking runs and long hex) withholds the smallest item a hit is in. The bytes are scanned once more, whole, and a hit there holds the whole record, since it means a bug. What was withheld is kept by field, rule and a keyed fingerprint, never the value, and before any push the bytes are checked again.
- **The confirmed task line** is the only text a person writes that crosses machines. It is shared only under `share.task: confirmed`, after its author wrote or confirmed it and the scanner passed it, and on a teammate's machine it is shown to people only: never in a note, an MCP answer or `status.json`.
- **One gate in.** A teammate's record is read from its ref's tip only, its size checked before it is read; then JSON without duplicate keys, floats or deep nesting, every field against the same grammar, the writer (the ref's person and device must be the record's, the commit's author one of that person's emails), a sequence that must grow, and this machine's own policy again. A record that fails is dropped with a reason from a closed set, shown in `orch status`: `too-large`, `bad-json`, `duplicate-key`, `bad-structure`, `newer-format`, `bad-grammar:<field>`, `writer-mismatch`, `unlisted`, `rollback` or `not-a-record`. Unknown fields are dropped and counted, never kept.
- **What reaches an agent.** A note about a teammate's branch is built from what git says of its commits and from cleaned identifiers: their handle, the branch, function and file names, line numbers, and only contract reasons of the forms Orchestraty itself writes. Their task line, email, device and the session ids in their record never reach a note.
- **Records are not signed yet.** Anyone with push access to the remote can write a ref under `refs/orchestraty/` in anyone's name; the writer check stops mistakes, not someone set on it. A teammate's claims only ever inform.
- **Public repositories.** The policy must say whether the repository is public, a public one also needs `public_sync: true`, and the anonymous-read probe keeps sync off when a repository the policy calls private can be read by anyone.
